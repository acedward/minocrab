#+title: M39 — Nonces, fee policy, and the administrator: the design note (written before sig-net's Compact lands)

* 0. Why this note exists, and its status
dmd (2026-09-05/06) asked, in order: how an administrator could set the
gas price instead of the user; then for two administrator abilities being
implemented in Compact by sig-net — UNSTICK (a blank replacement at a
stuck nonce with a higher fee) and BATCH (write-only insert, one flush
numbers N transactions from the last used nonce); then whether a wrong
nonce is a security issue and whether the Signet request counter is
load-bearing. This note is written BEFORE their contract is in the
corpus, so that reading it later is a prediction checked (the M31 method)
rather than a story fitted afterwards. Nothing here is built; M39 B–D
build it when the corpus refreshes.

* 1. The EVM nonce today: untrusted, and safely so
Every request circuit takes =evm_nonce= as a public input the prover
chooses; the circuit cannot check it against chain state. That is fine:
- The nonce does not change what the transaction DOES. Recipient, amount,
  calldata, gas envelope and signing path are all bound into the record
  the MPC hashes and signs; the nonce decides only whether and when it
  can mine.
- Too low → rejected at submission, never executes, the MPC attests
  failure, the requester refunds. Too high → waits for the gap; if it
  never fills, the MPC's timeout policy attests failure. Either way the
  requester hurts only themselves: a high nonce blocks nobody else.
- Two honest provers racing for the same next nonce: both prove, the MPC
  signs both, one mines, the other becomes "too low" and refunds. Wasted
  proving and a bad experience; no loss, no gained authority.
VERDICT: a liveness problem for the requester, not a security one. The
batch (§4) removes the race; nothing needs to trust the nonce more than
it does today.

** 1.1 CORRECTION (dmd, 2026-09-06): outstanding nonces ARE a security issue
"A properly designed contract should never have transactions that hang,
because they take up space and are a DOS vector." The verdict above
looked only at the requester's own loss and missed the SHARED resource:
a transaction that never mines — a too-high nonce, a fee below the
market — sits in the queue and in the MPC's pending set, blocks every
later nonce on that signing path, and any user can create one at will.
That is a denial-of-service against the contract, so the nonce is NOT
"untrusted and safely so".
THE RULE (dmd): in a contract, THE USER CANNOT PICK THEIR OWN NONCE AND
GAS PRICE. Users can ONLY create VALID requests: the contract assigns
the nonce (the flush, §4) and the contract sets the fee (the policy
cell, §3, or the constants until it exists). Every request circuit that
takes =evm_nonce= as a prover-chosen input — the deployed vault, the
Pending lineage today — is what §4 replaces, not a shape to keep beside
it. Queue clearing is the BREAK GLASS, not a user facility: an
administrator clears (unsticks, §5) when, for example, the gas price
moves so far that flushed transactions can no longer mine at the fee
they were signed with; only the administrator ever chooses a nonce or a
fee, and only for that.
CONSEQUENCES for the build (M39 C): =Queued::insert= takes neither a
nonce nor a fee; =flush= reads the fee from the contract, never from an
argument; the =Blank= replacement (§5) is the one place a nonce and a
fee are arguments, and it is administrator-gated; a contract exposing
an unbatched =Pending::request= with a user nonce is a design smell to
retire once =Queued= lands, not a supported second path. §1's three
bullets stay as the account of WHY a wrong nonce cannot steal, which is
still true; they no longer justify letting a user choose one.
STATUS (dmd, 2026-09-06): sig-net is going to fix the user-chosen nonce
in their Compact; this note and M39 C run AHEAD of that to explore the
design space, so the batch built here is a prediction of their shape,
not a port of it. Prediction P9 (added to §7): their request circuit no
longer takes a nonce or a fee from the prover.

* 2. The Signet request counter: load-bearing for FRESHNESS, not as a shared number
=signetRequestNonce= is read (=popeq=) and incremented in every request
and is an element of the record, hence of the request id. It is what
makes two otherwise identical requests distinct: without it they would
collide in the record map and — the part the unlinkability argument
rests on (notes/zkir-semantics.org §7, V4) — produce the same refund
commitment =H(sk, reqId)= for the same user twice. So: load-bearing.
It is NOT load-bearing as a SHARED counter. Freshness needs something new
per request, not agreement on a number. REQUESTER-SUPPLIED RANDOMNESS
bound into the record gives uniqueness with overwhelming probability; a
membership check on the resulting id catches a requester deliberately
reusing their own value, and that read touches a key only that
requester's request ever touches — contention-free across users.
CONSEQUENCE FOR THE BATCH (§4): if the insert still =popeq=s the shared
counter, two concurrent provers still race on that read, and batching
removes only one of the two races. TO CONFIRM against sig-net's
contract when it lands: does the insert read anything shared?

** 2.1 CORRECTION (dmd, 2026-09-06): the counter is REPLAY protection, not entropy
"The point of the counter is to prevent double spending of a single
response." Right: the property is LIFETIME UNIQUENESS of request ids, so
one attestation (the MPC's signature over =(reqId, output)=) settles
exactly one record, ever. Requester randomness alone opens a self-replay:
file, settle, file the same content with the same randomness, settle the
new record with the OLD signature for a transaction that never ran. A
self-keyed membership check on LIVE records does not see it (the first
record was consumed). MPC-side dedupe does not see it either — the
replay is an on-chain settlement of an old signature.
Entropy a user cannot control, in-circuit: none free — no beacon, block
time as bounds only, no view of the enclosing transaction; the only
values a prover cannot pick are those the contract's state assigns
MONOTONICALLY, and any monotone value READ in a proof is a contention
point by construction. So the choice is WHERE the one shared read sits.
THE ANSWER THE BATCH CONTAINS: the flush assigns each transaction an
EVM nonce from =last_nonce= — monotone for the key's lifetime, read once
per flush, chosen by the contract. Derive the request id AT FLUSH from
the pre-record AND the assigned nonce: unique forever, not requester-
chosen, one record per attestation. Requester randomness is only the
HANDLE (pre-record + env between insert and flush; the refund commitment
binds to it); it needs a self-keyed membership check and nothing more,
because nothing settles against a handle. Insert stays write-only; the
shared counter goes.
WHERE THAT DOES NOT REACH: user-derived signing paths (the vault's
deposit signs from the user's own key, whose EVM nonce is user-owned)
and any unbatched request. There, lifetime uniqueness without a shared
counter = a SPENT-ID SET: every filed id inserted into a never-pruned set
(write-only insert; membership checked on the requester's own key,
contention-free), a re-filed id rejected before any old attestation can
be replayed. Cost: one entry per request, forever. If that is
unacceptable, those flows KEEP the counter, now known to be doing one
job. Predictions P7: their flush derives the id from the assigned nonce
(or still from a counter read at insert); P8: deposit keeps a counter or
gains a spent set.

* 3. The fee policy: an administrator's cell, one read per request
Today the envelope is a contract constant (1 gwei priority, 30 gwei cap,
a per-call gas LIMIT). The limit is a property of the call and stays on
the call type (=EvmCall::GAS_LIMIT=). The two fees are market conditions
and belong in a =FeePolicy { max_priority_fee, max_fee }= cell in the
=Signet= block (or an =Admin= block beside it), written by a
=set_fee_policy= circuit gated on an administrator, and READ by every
request in place of the constants — one public read (=popeq=), a few
rows. The administrator: the deployer key the vault already gates
=initialise= on is the minimal choice; a rotatable admin commitment
(=Commit<AdminKey, AdminTag>= opened with a fresh witness, the same
construction as =Owned=) is the better one, because deployer keys are
cold. DECISION FOR DMD; the note recommends the rotatable commitment.
DECIDED (dmd, 2026-09-06, decisions.org A3): WAIT — the constants stay
in =erc20_vault= until this cell exists, and then the fee material moves
into a generic EVM TRANSACTION layer: ERC-20 token > EVM transaction >
sig transaction, with clean boundaries. The admin choice (deployer key
vs rotatable commitment) is still open; batching (§4) is built first,
with the request counter kept for now.

* 4. BATCH: write-only insert, one flush
The shape dmd described: a request circuit does not choose a nonce; it
INSERTS the transaction-minus-nonce (callee, calldata words, gas limit,
the fee policy read at insert or at flush — decide: at FLUSH, so a fee
change between insert and flush applies) into a structure whose insert
is WRITE-ONLY; a FLUSH circuit pulls N entries, reads =last_nonce= ONCE,
numbers them =last+1 … last+N=, writes =last+N=, and emits N sign events
in one transaction; the MPC signs and submits N consecutive txs.
Which Midnight ADT is write-only on insert: =List.pushFront= (an Impact
push, no read); a =Map= keyed by a requester-owned handle likewise. A
counter-keyed tail (=tail++= then insert at =tail=) is NOT: reading the
tail is the contention. So the queue is a =List= (LIFO order — nonce
order among a flush's N entries is whatever the flush pulls; fairness is
not a correctness property here) or a =Map= keyed by =H(pre-record ‖
requester randomness)= — the §2 key, which also serves as the handle the
requester keeps to find their request.
THE RECORD MOVES TO FLUSH: the record the MPC hashes contains the nonce,
so it cannot exist at insert. The queue holds a PRE-RECORD; the flush
creates N records and N request ids and notifies the singleton N times.
Consequences: (i) the settle side keys on ids the requester did not know
when they proved — the environment (who may refund, how much) is
attached at INSERT under the requester's handle and copied into the
record's env at flush, or the settle looks it up by handle; (ii) the
requester's refund commitment =H(sk, reqId)= can no longer be computed at
insert (no reqId yet) — bind it to the HANDLE instead (=H(sk, handle)=),
which is fresh per request by §2 and known to the requester; (iii) the
flush is the one circuit that reads shared state (=last_nonce=, the
queue head) — it is the contention point by design, run by anyone or by
the administrator, and a stale flush proof simply fails (its =popeq=s no
longer match) and is re-proven.
COST SHAPE: insert is cheaper than today's request (no counter read, no
record hash); flush pays N record hashes + N notifications in one
circuit — its k grows with N, so N is a per-contract const (=Queued<Call,
Env, WORDS, N>=) and a large N is a large circuit. Two or three flush
sizes may be worth having.

* 5. UNSTICK: a blank replacement, administrator only
A transaction that never mines at nonce n blocks n+1, n+2, … for the
key. The administrator asks the MPC to sign a BLANK at n — the key's own
address, zero value, no calldata, 21,000 gas — with a HIGHER,
administrator-chosen fee (the replacement rule: same nonce, fee bumped
by the node's minimum, typically 10%). As a call type: =Blank= with
=Args = ()=, =Return = Unit=, =succeeded = always=, callee = the signing
key's own address (read from the Signet block or derived), an EXPLICIT
nonce and an EXPLICIT fee envelope (the fixed default does not apply —
the whole point is to exceed the stuck fee).
This is a CANCEL-BY-REPLACEMENT power: whatever user transaction was
pending at n is displaced. Hence administrator-only, and its effect is
honest by construction: the MPC observes the replacement mine, the
original never executes, its request is attested FAILURE, and it routes
to the owner's =refund=. The MPC's side must recognise a replacement at
an already-issued nonce (M39 D: signet-sim).
OPTIONAL per contract: a contract without the =Admin= block has no
=unstick= and no =set_fee_policy= and compiles to the M37 shape unchanged
(zero movement on the treasury and the vault).

* 6. What stays PI-equal to sig-net, what our API does differently
PI-EQUAL (M39 B): whatever their Compact emits for insert / flush /
unstick / setFeePolicy — the compat port mirrors it op for op, as the
vault's port does. OUR OWN (M39 C): =Queued<Call, Env, WORDS, N>= beside
=Pending=, =Admin= with =FeePolicy=, the =Blank= call, the handle-keyed
refund commitment — the Pending lineage's shape, byte-identical where
the statement is the same and deliberately different where §2/§4 say
their design still races.

* 7. Predictions to check when their contract lands
P1 the insert reads the request counter (the second race survives).
P2 the queue is a List with pushFront. P3 the flush reads one nonce cell
and increments by N. P4 the refund commitment is computed at flush from
the reqId, so the requester must be present at flush OR the env carries
the commitment from insert. P5 unstick is a fixed-shape tx to self with
caller-supplied fees and nonce, gated on the deployer. P6 the fee policy
is either absent (fees stay constants) or a cell the deployer writes.
P9 (§1.1): the user-chosen nonce and fee are gone from their request
circuit; whatever assigns the nonce is contract state read once.

** The surface
=crates/minocrab-contracts/src/evm_flow.rs=, beside =Pending=:

plus =Handle= (the queue key, a =Uint<64, Public>= newtype),
=PreRecord<WORDS>= (callee ‖ key version ‖ words, a limb vector like
=EventRecordV2=), =QueueEntry<Env, WORDS>= (pre-record + env in one map
value), =HandleOwned<E>= (=Owned='s twin, carrying the handle),
=CommitBinding= (what a =Commit= binds to: =RequestId= or =Handle=),
=Inserted= (the insert's disclosure label set), and
=evm::build_tx_from_words= (=build_tx= from stored words). The =Ledger=
derive learned one more slot spelling (=Pending= | =Fired= | =Queued=).

NO NONCE AND NO FEE ARGUMENT ANYWHERE ON THE REQUEST SIDE (§1.1, dmd's
binding rule): =insert= takes callee, args and key version; =flush=
takes nothing at all. =Queued= REPLACES the Pending lineage's
prover-chosen =evm_nonce=; it is not a second path beside it, and the
note says so here so that a later reader does not read the two as
alternatives.

** The six defaults: four held, two changed
1. HELD — =Queued= is "=Pending= plus a queue", literally: it OWNS a
   =Pending= and delegates the settle side to it, so there is no second
   implementation of =complete=/=refund= and no copy of the record maps.
2. CHANGED — THE HANDLE IS THE SLOT'S OWN INSERT COUNTER, not the Signet
   request counter. The code proved the default wrong: =flush= files
   through =file_request=, which READS AND INCREMENTS the Signet counter
   once per record. If handles were Signet-counter values, a flush of N
   would consume N of them, and the handles either side of a flush would
   not be contiguous — =flushed_upto+1 ..= +N= would name keys that were
   never queue keys. So =Queued= owns =next_handle=. The requester's
   handle is still "a counter value, FIFO for free", and the insert's one
   shared read is still exactly the contention dmd chose to keep; it is a
   different cell from the one the record's freshness field comes from.
3. HELD — =flush(c)= pulls =flushed_upto+1 ..= flushed_upto+N=, asserts
   each present ("Queued request not found"), reads =last_nonce= once,
   numbers them =last+1 … last+N=, files N records through the SAME
   =file_request= (same record version, same id rule, env moved from the
   handle key to the reqId key, N notifications), then advances both
   counters by N. Partial flush not in this cut. Fees: =Envelope::fixed=,
   through =Queued::envelope= — one private method, the fee-policy seam.
4. HELD, AND CHECKED — =complete= / =refund= are =Pending='s, and
   =tests/evm_batch.rs::the_settle_side_is_byte_identical_to_pendings=
   serializes the ZKIR of a queued =complete= and of an unbatched twin's
   at the same field offsets and asserts the strings are equal. They are.
   The OWNER gate is the one thing that could not be identical: see
   "the refund path" below.
5. HELD — flush is permissionless: no gate, no witness of its own (its
   three witnesses per entry are the cross-call's cc-rand and entry-point
   limbs), no admin block, no unstick, no fee cell.
6. HELD — zero movement: =MINOCRAB_ZKIR_DUMP= over the 214 dumped
   circuits diffs EMPTY against main's baseline.

** THE N-CROSS-CALLS FINDING: nothing blocks N notifications from one circuit
Asked to check whether the xcall machinery and the singleton's
=signBidirectional= allow N calls from one circuit. THEY DO, and the
codebase already knew: =minocrab-ledger/src/calls.rs= documents
"=xcall='s =callTwice= calls the same target twice in one circuit and
compactc reads the cell twice", which is why a =Callee::Field= read is
deliberately UNCACHED per call site. Each call claims its own
=(address, entry point, commitment)= through =kernel_claim_contract_call=
and discloses its own =XcallEntryPointHash= / =XcallCommitment=; nothing
in the interface, the ledger ops or the singleton is per-transaction
one-shot. Measured, not assumed:
=a_flush_notifies_the_singleton_once_per_entry= asserts exactly N
communications commitments, N entry-point hashes, N request ids, N
records and N freshness asserts in the flush at N = 1, 2, 4. The
singleton side is unchanged: N =signBidirectional= calls are N ordinary
calls, and signet-sim answers all N off one caller state (rung D).

** The refund path as built
=H(sk, handle)= at insert, opened against the handle at settle:
- =CommitBinding= is a new trait with two impls — =RequestId<Public>=
  (pushes hi, lo, exactly what =Commit= pushed before, so every existing
  commitment is bit-for-bit unchanged) and =Handle= (pushes its one
  field limb). =Commit::to= / =open= are generic over it. The only cost
  at the call sites was a =, _= in the turbofish.
- =HandleOwned<E> { handle, owner, inner }= is stored in the queue at
  insert and moved verbatim into the =Pending= env map at flush, so the
  settle side HAS the handle without the requester being present at the
  flush and without a second lookup.
- =Queued::refund_to_owner= is =Pending::refund= then
  =owner.open(c, &sk, env.handle, "Not the owner")=. This is the ONE
  place default 4 could not be byte-identical, and it is byte-identical
  in everything but the two limbs hashed into the commitment.
- The requester finds their request id by reading the assigned nonce off
  the flushed record, as §4 said; nothing in the circuit needs it.

** The adversarial properties, and how far they are gated
There is still NO Rust executor that produces a v3 circuit's public
transcript from ledger state (notes/signet-async.org §9's BLOCKED note;
the M26 harness item dmd holds), so "this transaction is rejected" cannot
be run end to end for a new contract without writing a second 3.8k-line
hand model. What IS gated, on the emitted stream:
- flush with fewer than N queued fails — N "Queued request not found"
  asserts, one per window slot, at N = 1, 2, 4 (=a_flush_requires_every_
  entry_of_its_window=).
- a stale flush fails / a double flush of the same window fails — the two
  counter =popeq=s are there and are read once each
  (=the_flush_touches_the_two_counters_once_each=); a second flush of a
  flushed window finds =flushed_upto= moved AND the entries removed.
- settle before flush fails — the record map's "Request not found" assert
  is in both settles (=a_settle_needs_a_flushed_record=).
- wrong-handle refund fails — the "Not the owner" assert is in the refund
  and, deliberately, in NO completion (=a_refund_opens_the_requesters_
  commitment=).
- nonces consecutive from last_nonce, ids unique, N distinct
  attestations — signet-sim, rung D, on records of exactly the shape the
  flush files.
The one claim NOT gated anywhere: "the ids are equal to what =Pending=
would mint for the same record". It is true BY CONSTRUCTION (the same
=file_request= over the same =EvmTx=), and the settle side's
byte-identity is checked, but no test files the same call both ways and
compares ids, because minting one needs the executor.

** What is left
- PARTIAL FLUSH (a flush of fewer than N when the queue is short). Not in
  this cut; a contract wanting smaller batches declares a second slot.
  The obvious shape is a guarded per-entry block, which costs the
  =when=-scope discipline on every op of the entry.
- THE ADMIN BLOCK: =FeePolicy= cell, =set_fee_policy=, the administrator
  commitment (§3 recommends the rotatable one; dmd decides).
- UNSTICK (§5), and with it queue clearing as the BREAK GLASS (§1.1) —
  the only place a nonce and a fee are ever arguments.
- THE FEE CELL read at flush, through the =Queued::envelope= seam.
- The u64 edge: =last_nonce + N= is field arithmetic over a counter read;
  at =u64::MAX= the circuit would accept what the ledger's counter would
  not, which is §8-item-19's recorded overflow finding in its new home.
- M39 B's port, when sig-net's Compact lands: P9 (§7) is now checkable
  against this build as well as against their contract.

* 9. dmd's calls of 2026-09-07 (decisions.org T3, T4, T5)
T3, the handle: ACCEPTED — =Queued='s handle stays the slot's own insert
counter.

T4, the request counter's replacement — dmd: "Number the requests the
same way as the nonce (let me know if this is impossible)". IT IS
POSSIBLE for every batched request, and it is §2.1's own answer read
back: the record a flush files ALREADY carries the flush-assigned EVM
nonce (=tx_params.nonce=) beside the signing path, and the request id is
the Poseidon of the whole record, so =(path, nonce)= inside the preimage
gives every batched id lifetime uniqueness with NO shared counter — the
nonce is monotone for the key's lifetime and assigned by the contract
from one read per flush. The change is therefore a REMOVAL, not a new
mechanism: =flush= files its N records through a =file_request= variant
that does not read or bump =signet.request_nonce=; the record's
=request_nonce= field is filled with the flush-assigned number (the same
last+k the EVM nonce gets, or a per-slot request counter read once at
flush beside =last_nonce= — the former needs no new cell and is what
"the same way as the nonce" says), so the WIRE FORMAT of the record and
the MPC's id recompute are untouched: the reader hashes the record's
bytes and never checks the field against a counter. Contention moves
from the global Signet counter to the slot's =last_nonce=, which the
flush reads anyway — flushes of different slots stop contending with
each other. Uniqueness across slots: two slots on different signing
paths differ in =path=; two slots on the SAME path would share a nonce
sequence only if they shared =last_nonce=, which they do not — so the
rule is one =Queued= per signing path, an assert at build time (the
contract-level slot walk M32 gave us can check it). The unstick
replacement at an already-issued nonce is a DIFFERENT record (a =Blank=
to self, no calldata), so a different id.
THE CAVEAT (§2.1's "where that does not reach"): a request whose EVM
nonce the contract does NOT assign — the vault's =deposit=, signing
from the user's own key, and any unbatched =Pending::request= — has no
contract-assigned monotone number to hash, so it KEEPS the Signet
counter (one job: replay protection) or gains the spent-id set. Nothing
impossible, then; one path stays as it is until it moves onto =Queued=.
BUILD: with the Admin rung (below), since both touch =flush= and the
record's filing; P7 (§7) becomes a prediction about OUR shape as well.

T5, the administrator and the fee material — dmd: the ROTATABLE admin
commitment (§3's recommendation), and nonce, fees and value "should sit
on the base EVM transaction layer because everything needs it". So the
A3 hierarchy is now placed: the ERC-20 (interface) layer knows calldata
and the gas LIMIT (=EvmCall= / =Filing::GAS_LIMIT=, as built); the EVM
TRANSACTION layer — a type of its own, =EvmTx= or the existing
=EvmType2TxParams= promoted — owns =nonce=, =max_priority_fee=,
=max_fee= and =value=, and is where the =FeePolicy= cell is READ (at
flush, through the =Queued::envelope= seam) and where =unstick='s
explicit nonce and fee are the administrator's arguments; the sig layer
owns the record, the notification and the key. THE ADMIN BLOCK, to
build: =Admin { commitment: Commit<AdminKey, AdminTag>, fee_policy:
FeePolicy }= (rotatable: =rotate_admin= opens the old commitment with a
fresh witness and writes the new, the =Owned= construction), =set_fee_
policy= gated on it, =unstick= gated on it filing a =Blank= at an
explicit nonce with an explicit envelope; OPTIONAL — a contract without
the block compiles to the M37 shape unchanged (zero movement on the
treasury and vault is the gate). The fee constants leave =erc20_vault=
only when the vault's paths move onto =Queued= (P9).

** Against Queued as built (§8)
- Their INSERT is better than ours: keyed by the refund commitment, it
  reads only its own key. Ours reads and bumps =next_handle= — one shared
  read per insert, so two inserts against one state still exclude each
  other (§8 default 2). The fix is theirs: key the queue by the handle
  the requester already has (=Commit<sk, binder>=), drop =next_handle=;
  the flush then takes the keys as an argument, as #61's drains do.
- Their DRAIN is ours: one read of the request counter, one EVM-nonce
  base, N records, N notifications, kind-homogeneous, permissionless.
  Two differences: they advance the EVM counter per drained entry (no
  gaps on skips) where ours asserts every handle present; and their
  request id is =counter + slot= where §9 (T4) has ours moving to the
  flush-assigned nonce — #62's index rule is that idea in a different
  container.
- #62 is the design our §2.1 said did not exist: a monotone, contract-
  assigned number obtained WITHOUT a shared read, because the ledger
  assigns the position and the proof READS it from a path checked
  against a history of roots. It has no batch width and no flush
  contention; it pays state per request and a second transaction. If it
  merges, the compat port (M39 B) is a =HistoricMerkleTree= allocator,
  and =Queued= should grow a sibling — =Allocated<Call, Env, WORDS>= —
  with =request= / =assign= instead of =insert= / =flush=.
- #59's admin is the deployer key, not a rotatable commitment (T5 chose
  rotatable for ours); its gas LIMITS live in the ledger per kind where
  ours keep them on the call type. Ours is the stricter of the two for
  the limit (a call's gas is a property of the call); theirs lets the
  operator move it without a redeploy.

** 10.1 Contention audit of the four PRs (2026-09-08), from the compiled Impact
METHOD: each PR compiled with the pinned compactc 0.34.0 (=--skip-zk
--feature-zkir-v3=); =tools/compact-reads.py= walks the generated
=index.js= and names every =popeq= per circuit. A =popeq= is a read
CHECKED at apply time (onchain-vm/src/vm.rs: "cached is deprecated, it
has no effect"), so two proofs against one state both apply only if
neither reads what the other writes. =Counter.increment=, =Map.insert=,
=HistoricMerkleTree.insert= emit no popeq — CONFIRMED in the output, not
taken from the PR text (#62 =parkRequest= reads only =initialised= and
its own =pendingParams= key).

#58: =startDeposit= reads =depositRequestNonces[caller]= (member +
lookup) — per caller. Contention-free across callers; the same caller's
two deposits against one state still exclude each other (inherent to a
per-caller monotone). Every other flow unchanged: global counter.
#59: adds three admin-cell reads to every vault-signed request and to
=adminReplaceEvmNonce=. One-off contention: a =setGasParams= invalidates
every in-flight proof of those circuits — which is when the admin is
raising fees during a spike, exactly when in-flight requests exist. The
counter contention is otherwise #58's.
#61:
- =startWithdraw= / =startSwap= / =startSupply= / =startRedeem=: NO shared
  read. =initialised=, =kernel.self=, own =pendingVaultRequests= key, the
  stata constants. Contention-free. ✓
- =drain{Withdraws,Swaps,Supplies,Redeems}=: =signetRequestNonce= AND
  =vaultEvmNonce= (the latter once per drained entry, each a popeq), plus
  member+lookup on each key. ALL FOUR KINDS SERIALISE AGAINST EACH OTHER,
  not only within a kind; two drains with an overlapping key also lose
  the second on the key's member read.
- =approveStata= / =approveRouter=: NOT queued; read BOTH counters; gated
  only on =initialised= — PERMISSIONLESS. Anyone proving an approve races
  every drain, and a drain proven a block earlier is void once an approve
  lands. Cheap griefing of the drain path; the fix is to queue the
  approves too (which #62 did).
- =adminReplaceEvmNonce= reads =signetRequestNonce=: the break-glass
  proof is invalidated by every drain and approve that lands while the
  admin is proving. Retry-until-lucky under exactly the load the break
  glass exists for.
- Fee cells: as #59.
#62:
- =request*= (all six, approves included): =initialised=, own key.
  Contention-free. ✓  =assign*=: fee cells [admin], constants, own
  =pendingParams= key, =slots= root-history member (a set that only
  grows, so a stale root still passes), =evmNonceBase= (written once at
  initialise). NO shared counter anywhere in the user path. ✓
- =adminReplaceEvmNonce= reads =issuedSlots=, which EVERY =assign*=
  increments — the same break-glass liveness hole as #61, and here it is
  gratuitous: the guard ("nonce not issued yet") can be proven from the
  tree instead (a path for leaf =nonce − evmNonceBase= against the root
  history, contention-free), or the admin can be trusted with its own
  break glass and the read dropped. Only reader of =issuedSlots=.
- Fee cells: as #59. The cost is an EVM-nonce GAP for a parked request
  nobody assigns (anyone may; the MPC must tolerate out-of-order
  assigns), ~100 bytes of state per request forever, and two Midnight

* 11. flush_design.org's two-phase flush, costed (2026-09-09)

#+begin_src compact
pragma language_version >= 0.16;
import CompactStandardLibrary;
struct Entry { callee: Bytes<20>; keyVersion: Uint<8>; w0: Uint<128>; w1: Uint<128>;
               owner: Bytes<32>; handle: Uint<64>; amount: Uint<64>; }
struct Cooked { entry: Entry; nonce: Uint<64>; }
export ledger uncooked: Map<Uint<64>, Entry>;
export ledger withNonce: Map<Uint<64>, Cooked>;
export ledger nonce: Counter;
circuit flushA<#N>(numbers: Vector<N, Uint<64>>): [] {
  const base = nonce as Uint<64>;
  for (const i of 0..N) {
    const n = disclose(numbers[i]);
    assert(uncooked.member(n), "not queued");
    const e = uncooked.lookup(n);
    uncooked.remove(n);
    withNonce.insert(n, Cooked { entry: e, nonce: (base + i + 1) as Uint<64> });
  }
  nonce.increment(N);
}
export circuit flushA4(numbers: Vector<4, Uint<64>>): [] { flushA<4>(numbers); }
#+end_src
